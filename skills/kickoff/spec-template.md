# <Name of the work>

Status: draft | agreed

## Problem

What is wrong or missing today, from the user's side. Three or four sentences.

## Solution

What the user will be able to do when this is done. No technical detail.

## How we will know it worked

A short list of things that can be checked and could fail. Include what must
**not** change.

## Decisions

What was settled in the kickoff, grouped by area. Describe behaviour, data
shapes and interfaces. No file paths and no code: both go stale.

| Decision | Why | Who decided (user / agent, for the reviewer to check) |
|---|---|---|

## Where the tests sit

For each place tests will attach: what goes in, what is checked, what it
catches, what it misses. Name an existing test to copy the style from.

## Boundaries

- **Always:** things every ticket must do.
- **Ask first:** things that need the user's yes (new dependency, stored
  format change, anything that cannot be undone).
- **Never:** things no ticket may do.

## Out of scope

What is deliberately not being done, and why. New ideas that come up during
the build are parked here, not added to a ticket.

## Open questions

Each with who can answer it.
